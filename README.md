# BrikRS

Notion ライクな軽量 wiki / ミニブログ。

| 層 | 技術 |
|---|---|
| バックエンド | Rust / axum 0.8 / SeaORM 2.0（MariaDB） |
| フロントエンド | Vite / React / TypeScript / BlockNote 0.56 / Bootstrap 5.3（SCSS のみ。JS は使わない） |
| DB | MariaDB 11.4（既存の MariaDB に DB を1つ足して使える） |
| コンテナ | distroless（`cc-debian13:nonroot`）に実行ファイルと静的ファイルだけを置く。イメージ約64MB |

> **このプロジェクトについて**
> 個人で開発・運用している CMS を公開しているものです。0.x のあいだは、機能や設定・DB の構成が予告なく変わることがあります。
> 不具合の報告や要望は Issue で受け付けますが、対応や修正の時期・可否はお約束できません。利用は自己責任でお願いします（[LICENSE](LICENSE) のとおり無保証です）。
> コードとドキュメントの大部分は、AI のコーディング支援ツール（[Claude Code](https://claude.com/claude-code)）を使って書いています。仕様・設計の判断と、動作の確認・運用は作者が行っています。

## 起動方法

### A. コンテナで動かす（本番と同じ形）

```bash
docker compose up -d --build
docker compose exec brikrs_app /app/brikrs create-user admin --admin --name 管理者   # パスワードを入力（10文字以上）
# → http://127.0.0.1:8081
```

### B. 開発モード（ホットリロード）

```bash
docker compose -f compose.dev.yml up -d          # MariaDB（127.0.0.1:3307）
cd backend && cp -n .env.example .env
cargo run -- create-user admin --admin --name 管理者
cargo run                                         # API（127.0.0.1:8080）
cd ../frontend && npm install && npm run dev      # http://localhost:5173（/api・/uploads・フィードは 8080 へ中継）
# Docker のコンテナ（8081）を相手にするなら：BRIKRS_BACKEND=http://127.0.0.1:8081 npm run dev
```

## 初期データ（サンプルページ）

新しく入れた DB（ユーザーもページも無い）の初回起動で、次のページを自動で作る。自由に編集・削除してよい。

- 👋 BrikRS へようこそ（子ページ：📘 使い方ガイド、🎨 書式サンプル、📐 仕様と設計、🛠️ 運用ガイド）
- 💬 つぶやき（タイムラインの例。投稿4件、1件はピン留め）
- 📝 下書きのサンプル（管理者にだけ見える。サンプルのページには作った人がいないため）

内容と画像は実行ファイルに埋め込んである（`backend/src/seed.rs`、`backend/seed/`）。`SEED_SAMPLES=false` で作らない。既存の DB に足すときは `brikrs seed`。

新しい版でサンプルの内容が変わったら、`brikrs seed --update --user <username>` で入っているサンプルを上書きできる（先に `--dry-run` で何をするか確かめられる）。

- どのページがどのサンプルかは、`seed` のときに `site_settings` の `seed_pages` に記録する。記録の無い DB（0.10.2 までに入れたもの）では、初回だけタイトルと親子関係で探して記録する
- 上書きするのは本文・タイトル・アイコンだけ。ページ番号・位置・下書きかどうかは変えない。前の本文は編集履歴に残る（`--user` の人の編集として）。中身が同じなら何もしない
- 自分で作ったページ・投稿には触れない。削除したサンプルは作り直さない（ゴミ箱にあるものは、戻せば次から対象になる）。新しい版で足されたサンプルは作る
- 消したサンプルへのページリンクは、タイトルの文字だけにする

## 機能

- **閲覧は公開、編集はログインした編集者のみ**。複数の編集者を管理者が追加・管理
- **管理画面**（管理者のみ。ナビバーの「管理」）：「ユーザー」「アクセス解析」「ログイン監視」のタブ。期間は 7 / 30 / 90日
  - アクセス解析：ページビュー、ユニーク訪問者、セッション、日別の推移、よく見られているページ、参照元。ログインしている編集者の閲覧と bot（User-Agent で判定）は数えない
  - ログイン監視：試行・失敗の数、日別の失敗、IP ごとの失敗（期間内に5回以上なら「⚠ 要注意」）、最近の失敗（パスワード / 2段階認証 / 回数制限で拒否）
  - 記録は IP アドレスを含むので、定期的な掃除で古いものを消す（`LOG_RETENTION_DAYS`、既定 180日）
- **ゲストコメント・リアクション**（タイムライン）：管理画面のサイトタブで有効にし、タイムラインのページごとに「…」メニューで受け付ける。表示形式をタイムライン以外にすると、表示も受け付けもしない（データは残る）
  - ゲストコメント：ログインしていない人がタイムラインの投稿にコメントできる。管理者が「管理 › コメント」で承認するまで公開しない（却下は削除）。本文はただのテキスト（名前30文字・本文1000文字まで）。管理者は公開中のコメントに返信できる。投稿した人は自分のコメントを削除できる
  - 送信の対策：画像の CAPTCHA（このサーバーで生成、外部サービスなし。サイトタブで切り替え）、使い捨てのフォーム用トークン、ハニーポット、IP ごとの回数制限、承認待ちの総数の上限、ログインユーザーと同じ名前の禁止
  - リアクション：誰でも投稿・返信に 👍 ❤️ 😂 😮 🎉 を付けられる（件数は公開）。同じ人の重複は Cookie と IP ごとの上限で防ぐ（目安）
  - IP アドレスと User-Agent は `GUEST_IP_RETENTION_DAYS`（既定 90日）を過ぎたら消す。承認されないままのコメントも削除する
  - 承認待ちのメール通知（任意）：`SMTP_SERVER`・`SMTP_PORT`（既定 465、SMTP over SSL）・`SMTP_USER`・`SMTP_PASSWD`・`MAIL_FROM`・`COMMENT_NOTIFY_TO`（宛先、カンマ区切り）を設定すると、承認待ちが出たときに知らせる。数分ごとにまとめて1通（名前・投稿のタイトル・本文の先頭100文字・管理画面の URL。IP は入れない）、送ったあと30分は送らない。設定の確認は `brikrs mail-test`
- **2段階認証**（任意）：「アカウント」で認証アプリ（Google Authenticator など）を登録すると、ログイン時に6桁のコードも求める。認証アプリを失くしたときのリカバリーコード（使い捨て10個）付き。管理者はユーザー管理から他の人の2段階認証を解除できる。管理者自身が締め出されたときは `brikrs reset-totp <username>`
- **ページ**：作成・編集、階層ツリー（ドラッグ＆ドロップで並べ替え・入れ子）、アイコン、パンくず、子ページ一覧、バックリンク（このページへリンクしているページの一覧）
- **レイアウト**：上部のナビバーと左のカード型のページツリー。スマホ幅ではナビは折りたたみ、ページツリーは左から出るパネルになる。文字は端末の標準のフォント（Web フォントは使わない）。配色は OS の設定に合わせたライト / ダーク
- **カラーテーマ**：「アカウント」の「表示」で「OS の設定に従う」「ライト」「ダーク」を選べる。アカウントに保存するので、別の端末でログインしても同じになる（ログインしていない閲覧者は OS の設定に従う）
- **閲覧画面**：未ログインの閲覧者には BlockNote を配らず、軽い自前の描画（`BlockView`）で表示する。編集者は BlockNote を後から読み込む
- **ブロック編集**：BlockNote（`/` でブロック挿入メニュー）、0.8秒後に自動保存
- **公開範囲**：ページの「…」メニューの「公開範囲・下書き…」で、公開（誰でも）・登録ユーザー（ログインしている人）・グループ（選んだグループの人と管理者）から選ぶ。子ページにも効き、祖先の範囲もすべて満たす人だけが見られる。見られない人にはツリー・検索・最近の更新・バックリンク・フィード・OGP のどこにも出ず、URL を開いても 404。タイムラインの投稿欄でも、投稿ボタンの横で選べる
- **下書き**：同じダイアログで切り替える。作った人と管理者にだけ見える（子ページも含む）。下書きを外すと、選んでおいた公開範囲になる
- **グループ**：管理画面の「グループ」タブで作成・削除し、ユーザーを入れる（1人が複数のグループに入れる。新しいユーザーはどこにも入っていない）。管理者は特別なグループの扱いで、全部のページを見られる
- 公開範囲・下書きを変えられるのは、ページを作った人と管理者だけ。管理者以外は、自分が入っているグループを1つ以上含めないと保存できない（自分も見られなくなるため）
- ページの移動で、親ページの下書き・公開範囲の制限が変わる（制限の外へ出す・制限のあるページの下へ入れる）ときも、できるのは作った人と管理者だけ。サイドバーのドラッグでは確認を出す。同じ制限の中での付け替えは誰でもできる
- **ロック**：「…」メニューの「🔐 ロック」で、作った人と管理者のほかは閲覧だけにする（本文・タイトル・設定の変更、版の復元ができない）。ロック中は作った人・管理者も移動・ゴミ箱へ移すことはできず、先にロックを外す。ロックはそのページ自身だけに効き、子ページ（返信・データベースの行）には効かない。ロックの下に子ページを作る・返信することはできる。子孫にロック中のページがあると、親ページもゴミ箱へ移せない（ロックを外せるのはそのページを作った人と管理者なので、作った人がばらばらのときは管理者が外す）。CLI の `page move`・`page trash` も同じく断る
- **最近の更新**：ナビバーから。更新の新しい順に30件（タイムラインの投稿は除く）。`/feed.atom` で Atom フィードも配信
- **タイムライン（ミニブログ）**：「…」メニューで「タイムライン表示にする」と、子ページを投稿として新しい順に本文ごと並べる（スクロールで続きを読み込む）。編集者には上部に投稿欄が出て、書いて「投稿」（Ctrl+Enter）すると子ページになる（タイトルは本文の1行目から自動）。投稿はツリーには出さず件数だけ表示。`/p/<id>/feed.atom` でタイムラインのフィード
- **月別アーカイブ**：タイムラインの「📅 アーカイブ」で月を選ぶと、その月の投稿だけを表示（月ごとの件数付き、ピン留めも日付順に並ぶ）。URL は `/p/<id>?month=2026-10`。月の区切りは閲覧している人のタイムゾーン
- **ピン留め**：タイムラインの投稿の「📌 固定」で先頭に固定する（複数可）
- **データベースページ**：「…」メニューで表示形式を「データベース」にすると、子ページを型付きの列（テキスト・数値・選択・日付・チェックボックス・URL）を持つ「行」として表で並べる（Notion のデータベースのような機能）。「⚙ 列を編集」で列を増減・変更、「＋ 行を追加」で行を増やす。行は普通の子ページなので開けば本文も書け、検索・最近の更新・バックリンクにも通常のページと同じように出る
- **ページテンプレート**：「…」メニューの「テンプレートにする」を付けたページは、以後どこからでも「テンプレートから作成…」で選んで、本文・アイコンをコピーした子ページを作れる
- **ブロックスニペット**：「/」メニューの「スニペットを管理」から、よく使う複数ブロックの組み合わせを名前・絵文字付きで登録しておける。「/」メニューから1回のクリックでまとめて挿入できる（ログインしている編集者なら誰でも作成・編集・削除できる）
- **数式**：「/」メニューの「数式（ブロック）」「数式（インライン）」から LaTeX を書き、KaTeX で表示する（数式を含むページを開いたときだけ KaTeX を読み込む）。文中で `$…$` と打つとインライン数式に、行頭で `$$` + 空白、または `$$…$$` だけを打つと数式ブロックになる。「$5 と $10」のような金額や、インラインコードの中では反応しない
- **YouTube**：「/」メニューの「埋め込み」→「YouTube」で動画の URL を貼ると埋め込む。最初はサムネイルだけを出し、再生ボタンを押したときに初めてプレーヤー（youtube-nocookie.com）を読み込む
- **Google マップ**：「/」メニューの「埋め込み」→「Google マップ」で、場所のページの URL、「共有」→「地図を埋め込む」のコード、マイマップの URL（または「自分のサイトに埋め込む」のコード）を貼ると地図を埋め込む。iframe は `loading="lazy"` で、画面に近づいてから読み込む。ページには地図を表す値（埋め込みコードの `pb`・マイマップの `mid`・場所の名前と座標）だけを保存し、URL は表示のたびに組み立てる。場所の URL は API キーの要らない `output=embed` で表示する（Google が公開している方法ではないので、将来使えなくなる可能性がある）。短縮 URL（maps.app.goo.gl）は使えない。マイマップは「リンクを知っている全員」に公開しておく
- **X（Twitter）の投稿**：「/」メニューの「埋め込み」→「X（Twitter）の投稿」で投稿の URL（x.com・twitter.com）を貼ると、X の oEmbed（publish.x.com、公開の API）から投稿者・本文・日付を読み込んでカードで表示する。内容はページに保存し（表示のたびに X へ取りに行かない。元の投稿が消されても残る）、編集画面の「↻」で取り直せる。画像・動画は保存せず「画像・動画あり」の印だけを出し、カードの「X で表示」を押したときに初めて公式の表示（platform.twitter.com の iframe）を読み込む。X の widgets.js は使わない。本文も検索の対象
- **GitHub Gist**：「/」メニューの「埋め込み」→「GitHub Gist」で Gist の URL を貼ると、ファイルの内容を GitHub の API から読み込んでコードとして表示する。内容はページに保存し（表示のたびに GitHub へ取りに行かない）、編集画面の「↻」で最新の内容を取り直せる。コードも検索の対象
- **目次**：見出しが2つ以上あるページで、広い画面は左のページツリーの下、狭い画面はページ上部に出す。クリックでその見出しへ移動。編集中は保存のたびに更新
- **ハッシュタグ**：本文の `#Rust` のような語をクリックすると、そのタグで検索する（閲覧画面とタイムラインで。編集画面ではふつうの文字）。URL の `#section`、数字だけの `#1` は対象外
- **共有用のタイトル・説明（OGP）**：`/p/<id>` の HTML の `<head>` に、ページのタイトル・本文の冒頭・最初の画像を入れる。X などに貼るとカードになる
- **Markdown の貼り付け**：VS Code からコピーした Markdown や、HTML 付きでも中身が明らかに Markdown のテキストは、見出し・リスト・コードなどの書式として貼られる（VS Code からのそれ以外の言語のコードは従来どおりコードブロック）
- **ページリンク**：本文で `@` → ページを選ぶとリンクになる。リンク先を改名しても最新のタイトルで表示される。一致するページが無ければ、その場で子ページとして作成してリンクできる
- **検索**：`Ctrl+K`（⌘K）。スペース区切りで AND 検索。タイトルと本文が対象で、ヒット箇所を強調表示
- **画像**：`/画像` からアップロード、または貼り付け。PNG / JPEG / GIF / WebP、10MBまで
  - 画像を選んで出るツールバーの「左に回り込み」「右に回り込み」で、文字を回り込ませる（幅は本文の 40%、ハンドルで変更可。スマホの幅では回り込ませない）。閲覧画面は文字が画像の下まで回り込み、エディタは段落ごと画像の横に並ぶ
  - 表のセルの中にも置ける（セルで「/」→「画像」、貼り付け、ドロップ）。大きさは列の幅に収まり、列の幅は閲覧画面でもエディタと同じ。表の左のつまみのメニューの「枠線なし」で、写真を並べるのに使える
  - 大きな画像の縮小（任意）：管理画面のサイトタブで長い辺の上限（1280〜3840 px）を選ぶと、JPEG・PNG・WebP をブラウザで縮小してから送る（Exif は残らない。GIF はそのまま）
- **編集履歴**：ページの「履歴」から過去の版を表示・復元（編集者のみ）。同じ人の15分以内の連続した編集は1つの版にまとめる。ページごとに新しい100件まで残す
- **同時編集の衝突検知**：他の人が先に保存していたら、保存せずに知らせる。「自分の変更で上書き」か「自分の変更を捨てて最新を読み込む」を選ぶ（どちらでも相手の版は履歴に残る）。タブに戻ったとき、未保存の変更が無ければ最新を読み直す
- **ゴミ箱**：「ゴミ箱へ」で子ページごと移動。ゴミ箱画面から復元・完全削除・空にする。親がゴミ箱にある状態で子だけ復元すると最上位に出る（親の下書き・公開範囲の制限を受けていたページは、制限が外れないよう下書きにして戻す）。30日経つと自動で完全に削除する
- **タイムラインの返信**：投稿の「💬 返信する」から返信でき、返信にも返信できる（返信は投稿の子ページとして保存する）。返信は投稿の下に新しい順の木で出し、「▸ 返信 N件」で畳める（返信が4件以上なら最初は畳む。開閉はブラウザに覚える）。投稿・返信の日時から開くと、元の投稿からの流れと、そのページへの返信が一緒に出る。見出しの「🗑」で、その投稿・返信を下の返信ごとゴミ箱へ移す（編集者のみ）。返信は最近の更新・フィードには出さない
- **CLI からの投稿・読み出し**（`brikrs page`）：サーバーに SSH で入ってコンテナで実行する前提で、認証なしで DB に直接つなぐ（`create-user` などと同じ扱い）。Claude Code などからの自動投稿・記事の読み出し用で、本文は Markdown で受け渡す。投稿は Web から作ったときと同じく、検索・バックリンク・編集履歴に反映される
  ```sh
  docker compose exec -T brikrs_app /app/brikrs page list                 # ツリー順の一覧（--json も可）
  docker compose exec -T brikrs_app /app/brikrs page get 12               # 1ページを Markdown で（先頭に id・タイトルなど。--json は BlockNote のまま）
  docker compose exec -T brikrs_app /app/brikrs page export > pages.json  # 全ページを JSON の配列で
  docker compose exec -T brikrs_app /app/brikrs page post --user admin --parent 5 < note.md
  #   先頭の「# 見出し」がタイトルになる（--title で指定も可）。--draft で下書き、--icon で絵文字
  #   --members でログインしている人だけ、--group <グループ名> でそのグループの人だけ（複数指定可）
  docker compose exec -T brikrs_app /app/brikrs page thread 33             # タイムラインの投稿を、返信の木ごと Markdown で
  docker compose exec -T brikrs_app /app/brikrs page post --user admin --reply-to 33 < reply.md  # 投稿・返信への返信
  docker compose exec -T brikrs_app /app/brikrs page move 40 --parent 33   # 別の親の下へ移す（トップの投稿を返信に付け替えるなど。root で最上位）
  docker compose exec -T brikrs_app /app/brikrs page trash 40 --user admin # 子ページ（返信）ごとゴミ箱へ
  ```
  扱う書式は見出し・段落・リスト・チェックリスト・引用・コード・区切り線・画像（URL のみ）・表・数式（`$$…$$`）・YouTube・Google マップ・X の投稿（URL だけの段落。X の投稿は ID だけを持つカードになり、本文は編集画面の「↻」で取る）と、太字・斜体・取り消し線・インラインコード・リンク・インライン数式（`$…$`）。段落内の改行はそのまま改行になる。今は新規作成だけで、既存ページの上書きはしない
- **定期的な掃除**（6時間ごと。`brikrs maintenance` で手動実行も可）：古いゴミ箱のページ、上限を超えた履歴、どのページ・履歴・スニペットからも使われていない画像（アップロードから24時間以上経ったもの）、期限切れのセッション。日数と件数は `TRASH_RETENTION_DAYS` / `REVISION_KEEP` で変更でき、0 で無効

## 設計メモ

- **配色は Bootstrap の変数に集約**：`frontend/src/styles/theme.scss` で Bootstrap の色を決め、アプリ側の CSS（`--bg`、`--text` など）はそれを参照する。ライト / ダークは `<html data-bs-theme>` で切り替え、値は `src/theme.ts` が決める（選んだ設定は localStorage とアカウントに保存）。描画前の色は `public/theme-init.js` が決めるので、読み込み直しても一瞬違う色が見えることはない。テーマを増やすときは `[data-bs-theme='名前']` で変数を上書きする
- **アイコンはサイトごとに差し替えられる**：同梱しているのは汎用の BrikRS アイコン（`frontend/scripts/default-icon.py` で描いたもの）。`BRANDING_DIR`（コンテナでは `/data/branding`）に favicon.ico・icon-192.png・icon-512.png・apple-touch-icon.png・manifest.webmanifest を同じ名前で置くと、そちらを優先する（置いたものだけが置き換わる）。一式は `python frontend/scripts/make-icons.py <正方形の元画像> <出力先>` で作れる（不透明な画像なら背景を自動で透明にする）。ナビバーのロゴと、本文に画像の無いページの共有カード（OGP）も同じアイコンを使う
- **サイトのタイトルは管理画面で**：ロゴ・タブ・フィード・共有カード（OGP）のサイト名は `site_settings` 表に保存し、起動時に読んでメモリに持つ（HTML を返すたびに DB を引かない）。index.html の `<title>` はサーバーが差し替える。管理画面で一度も保存していなければ環境変数 `SITE_NAME`（無ければ BrikRS）を使う

- **検索を LIKE にした理由**：MariaDB の FULLTEXT は日本語の分かち書きができない（ngram パーサーは MySQL 専用、Mroonga は追加のプラグインが必要）。保存時に本文からプレーンテキストを抜き出して `pages.search_text` に入れ、`LIKE` で検索する。`%` `_` はエスケープ済み。個人・身内用の規模（数千ページ程度）なら十分速い
- **ページの削除**：InnoDB の `ON DELETE CASCADE` は入れ子15段までしか辿らないので、完全削除のときは子孫を自前で集めて深い方から消す
- **履歴を残すのは保存後の状態**：版を復元すると、その操作も新しい版として残る（直前の編集が上書きされないよう、復元時は必ず新しい版にする）
- **衝突検知は版番号で行う**：`pages.version` を保存のたびに1つ増やす。クライアントは元にした版を `base_version` で送り、違えば 409 と最新のページを返す。確認と加算の間に他の保存が割り込まないよう、行ロック（`SELECT ... FOR UPDATE`）を取る。クライアントは保存を1つずつ順に送る（並行して送ると自分の保存同士が衝突する）
- **バックリンクはリンク表で持つ**：保存時に本文から `pageLink` と `/p/<id>` へのリンクを抜き出して `page_links` を作り直す。リンク先は削除済みでも行を残す（復元すればまた出る）
- **未使用の画像の判定**：ゴミ箱を含む全ページ・全履歴・全スニペットの本文から `/uploads/<保存名>` を集め、どこにも出てこない画像を消す。履歴の上限で古い版が消えれば、その版だけが使っていた画像も消える
- **buildx でビルドしたイメージはクラシックビルドのイメージとレイヤーを共有しない**：`docker buildx build --platform ...`（`push-host-image.sh`）はベースイメージ（distroless など）のレイヤーを再パッケージするため、同じ内容でも `docker build`（`push-image.sh`）で作った過去イメージとは digest が変わり、サーバー上で重複排除されない。動作への影響は無いが、ベースレイヤー分（数十MB程度）だけディスク使用量が余分に増える。以後 buildx 側に統一すれば、buildx どうしでは重複排除される

- **タイムラインは「子ページ = 投稿」**：投稿用の別のデータは作らない。検索・履歴・ゴミ箱・リンク・画像がそのまま使える。表示形式は `pages.layout`（page / timeline）
- **公開範囲の判定**（`backend/src/access.rs`）：見ている人（`Viewer`：ゲスト／ユーザー・管理者か・所属グループ）ごとに、自分か祖先のどれかが見られなければ非公開。下書き（`is_draft`）と公開範囲（`pages.visibility`、`page_groups`）は別の列で持つ。読み取りの API・フィード・OGP はすべて同じ関数（`hidden_for`）で絞り込む
  - 書き込みの API（更新・設定・移動・ゴミ箱・履歴・子ページの作成）も、見えないページは 404。ログインしていても、見えないページは編集できない
  - 祖先で範囲を限ったページを別の親へ移すと見える人が増えることがあるので、親を変えられるのはそのページを作った人と管理者だけ。見えないページ（他の人の下書きなど）を子孫に含むページは、ゴミ箱へ移せない・完全に削除できない（管理者は除く）
  - 公開範囲を限ったページの画像は、URL を知っていれば見られる（保存名は推測できないランダム。下書きと同じ）
- **ロック**（`pages.is_locked`）：見られる人は編集もできる、という今までの決まりの例外。編集の判定は `ensure_editable`（本文の更新・設定・版の復元）、移動・ゴミ箱の判定は `ensure_unlocked`（`move_to`・`trash_page` の中なので API と CLI の両方に効く）。ロックしたページはゴミ箱に入らないので、ゴミ箱の復元・完全な削除では見ない

## セキュリティ

- パスワード：argon2id。存在しないユーザーでもダミーの検証を行い、応答時間でユーザーの有無が分からないようにする
- セッション：256bit のランダムなトークンを HttpOnly / SameSite=Lax の Cookie に入れ、DB には SHA-256 だけを保存。有効期限は14日
- CSRF：変更系のリクエストには `X-CSRF-Token` ヘッダーが必須
- ログイン失敗の回数制限：IP 単位とユーザー名単位で、それぞれ15分に10回まで（2段階認証のコードの失敗も数える）
- 2段階認証（TOTP, RFC 6238）：HMAC-SHA1・6桁・30秒、時計のずれは前後30秒まで許容。同じ区間のコードは一度しか通らない（最後に使った区間を記録）。パスワードが通った後のコード待ちは5分・5回まで。リカバリーコードは SHA-256 だけを保存し、条件付きの UPDATE で消費するので同時に二重使用できない。有効にしたときは他の端末のセッションを無効にする。秘密鍵は DB に平文で入る（パスワードハッシュと同じく DB のバックアップの扱いに注意）
- XSS：本文は BlockNote の JSON として保存し、表示は BlockNote か自前の `BlockView`（React の要素として組み立てる）が行う（生の HTML は解釈しない）。保存時に `href` / `url` / `src` を検査し、`http(s)`・`mailto`・相対パス以外は空にする。`BlockView` も表示時に同じ検査をし、色は決まった色名のクラスにだけ変換する
- アップロード：形式は拡張子ではなくファイル先頭のバイト列で判定する。SVG は拒否。保存名はランダム（128bit）で、置き場所は静的ファイルとは別のディレクトリ。`nosniff` を付けて配信する
- SSRF（Web ブックマーク・Gist・X の投稿の取得）：http(s) の 80・443 番だけ。名前解決した IP がすべてグローバルなアドレスであることを確かめ、リダイレクトの行き先ごとに同じ検査をする。システムのプロキシは使わない。さらに、このサーバー自身のグローバル IP（`OGP_DENY_IPS`、未設定なら `PUBLIC_URL` のホスト）にも接続しない。コンテナから自分のグローバル IP へつなぐと、リバースプロキシには Docker の内部 IP からの接続として届くため、プロキシに「内部 IP なら許可」の設定があるとそこを覗けてしまう。`PUBLIC_URL` が CDN の後ろにあるときは、`OGP_DENY_IPS` にサーバーの IP を直接書く（CDN の IP を拒否すると、同じ CDN の他のサイトが取れなくなる）
- ヘッダー：CSP（`script-src 'self'`。iframe は `frame-src` で youtube-nocookie.com・www.google.com・platform.twitter.com だけ）、`X-Frame-Options: DENY` など
- コンテナ：distroless・nonroot で動かし、シェルは入れない。ヘルスチェックは `brikrs healthcheck` で行う

## バージョンとリリース

バージョンはシステム全体で1つ。`backend/Cargo.toml` が正本で、`frontend/package.json` も同じ番号にする（食い違うとフロントのビルドが止まる）。変更点は [CHANGELOG.md](CHANGELOG.md)。

- 確認：`brikrs --version`、起動時のログ、「アカウント」画面（ログイン中のみ。画面とサーバーの版が違えば再読み込みを促す）
- 番号（0.x 系）：機能追加・DB のマイグレーションを含む → `0.x.0`、不具合の修正だけ → `0.x.y`

リリースの手順：

```bash
scripts/bump-version.sh 0.2.0          # Cargo.toml / Cargo.lock / package.json / package-lock.json を更新
# CHANGELOG.md に 0.2.0 の変更点を書く
git commit -am "BrikRS 0.2.0" && git tag -a v0.2.0 -m "BrikRS 0.2.0"
deploy/push-image.sh myserver          # brikrs:0.2.0 と brikrs:latest を作ってサーバー（ssh 先）へ転送
```

前の版に戻すときはサーバーで `BRIKRS_TAG=0.1.0 docker compose up -d`（DB のマイグレーションを含む版をまたぐときは DB のバックアップも戻す）。

## サーバーへのデプロイ

リバースプロキシ（nginx など）と既存の MariaDB があるサーバーに、イメージだけを持ち込む形（サーバー上ではビルドしない）。

1. 開発機で `deploy/push-image.sh <ssh 先>` を実行（`brikrs:<バージョン>` と `brikrs:latest` を作り、`docker save | ssh <ssh 先> docker load` で転送）。開発機が amd64 でない場合（Apple Silicon の Mac など）は `deploy/push-host-image.sh <ssh 先>` を使う（buildx で `linux/amd64` を明示してビルドする。ローカルのタグは `brikrs-amd64:<バージョン>` にして、ローカル確認用の `brikrs:latest`（ネイティブ architecture）と区別する）
2. サーバーに [deploy/compose.example.yml](deploy/compose.example.yml) を `compose.yml` として置き、`.env` に `DATABASE_URL` を書く
3. MariaDB に `brikrs` データベースとユーザーを作る（文字コードは utf8mb4）。DB のバックアップの対象にも加える
4. リバースプロキシで公開するドメインを BrikRS（コンテナの 8080 番）へ中継し、HTTPS の証明書を用意する
5. `docker compose up -d` → `docker compose exec -it brikrs_app /app/brikrs create-user admin --admin --name 管理者`
6. アップロード画像の置き場所（`./data`）は DB とは別にバックアップする
